# Gameplay / Core Loop

This dimension answers the most basic question in game review: once the player starts playing, is there a loop worth repeating? A surprising number of submissions have an idea, a control toy, or a visual wrapper, but not a true loop. Your job is to separate concept from loop, and loop from satisfying loop.

First principle: gameplay has to be fun. In review terms, "fun" is not a vibe word. It means the build creates at least one real reason to keep playing through challenge, tension, mastery, novelty, risk, timing, planning, score pressure, or meaningful consequences. If the player can complete the loop without needing to make decisions or improve, the loop is not working yet.

## Comparison discipline

Before judging the loop, identify what kind of game this wants to be in the player's mind. Compare against successful games with a similar loop structure, pressure curve, and session expectation.

Examples:

- score-attack survivors should be thought against games like `Vampire Survivors`, `Brotato`, or `Nova Drift`
- run-based action games should be thought against games like `Hades`, `Dead Cells`, or `Enter the Gungeon`
- small puzzle loops should be thought against games like `Baba Is You`, `Mini Metro`, or `Dorfromantik`

The comparison is not "does this have as much content as those games." The comparison is "does the core loop already create the same kind of clarity, motivation, and repeatability at its current stage."

## What to inspect

Look for the exact loop:

- what the player does
- what response the game gives
- what short-term goal the player chases
- what state changes make the next action meaningful
- what creates challenge, tension, mastery, or consequence

You should be able to describe the loop in one or two sentences. If you cannot, that is already a warning sign.

Identify the primary verb explicitly. If the player cannot perform that verb, the game does not have a core loop for this submission. For example, a darts game without a working throw interaction is `1/10` gameplay, not a rough or early-stage `5/10`.

Identify the challenge source explicitly. If challenge is absent because inputs are wrong, failure cannot happen, success is automatic, or level design is placeholder, cap gameplay at `3/10` and do not pass the review.

## Evidence to gather

- reach the main playable state as quickly as a new player would
- prove the primary verb works through direct interaction
- complete the loop at least once
- continue long enough to see whether the loop compounds, varies, or collapses
- note the point where engagement rises, flattens, or dies

If the loop only feels good after a hidden understanding step, call that out. A real loop should not require reviewer charity to become legible.

## Questions to answer

- Is the core action immediately understandable?
- Is there a reason to do it again?
- Does the game create momentum through escalation, mastery, novelty, score, progression, or risk?
- Does failure teach the player something useful?
- Does the loop produce decisions, or only motions?
- Is the player ever challenged by timing, aim, planning, risk, resource limits, positioning, score pressure, or constraints?
- Would a normal player have any reason to replay after understanding the trick once?

## Common failure modes

- the player can act, but there is no meaningful consequence
- the game presents the promise of a genre but omits the primary verb, such as throwing in darts or steering in driving
- the session starts with too much setup before the real loop begins
- the loop repeats without variation, pressure, or reward
- the level design is placeholder and does not force decisions
- the input model removes the skill the genre promise depends on
- the player can win by going through obvious motions with no tension or chance to improve
- the core action is readable only after frustrating trial and error
- the game has systems, but no unifying loop connecting them

## Stage-aware interpretation

At `Gameplay Prototype`, the loop can be rough, but it still needs to be testable and understandable. At `Demo`, it should already communicate why the game is worth caring about. By `First Release`, the loop should no longer depend on the reviewer imagining future potential.

Stage awareness never rescues an absent primary interaction. If the central action cannot be performed, cap gameplay at `1/10` and use `Blocked` unless another meaningful playable mode exists in the submitted build.

## What strong feedback looks like

Good notes name the exact loop weakness:

- "The dodge-attack-reward loop is visible, but the reward side is too flat, so the game feels closer to a movement test than a real combat loop."
- "The puzzle interaction is clever, but reset friction kills repeat attempts, which weakens the loop compared with stronger score-chasing puzzle games."

Weak notes like "needs more fun" or "needs more gameplay" are not acceptable.
